# Чабани — вода + світло

Telegram-бот для Чабанів, який **автоматично бере підтверджені графіки ДТЕК** з відкритого репозиторію [XOTT69/dtek](https://github.com/XOTT69/dtek), використовує групу **1.2** для розрахунку води та групу **2.2** для світла вдома. Ручне пересилання графіків більше не потрібне.

## Логіка

- якщо за підтвердженим графіком у групи 1.2 є світло — вода є (фактичні аварії можуть відрізнятися);
- якщо група 1.2 відключена — діє резервний графік води;
- резервний графік можна оновити окремим пересланим повідомленням;
- бот рахує воду, світло 2.2 і спільні вікна вода + світло.

## 🤖 Автосинхронізація з ДТЕК

Уже наявний Cloudflare Worker `botvoda` працює за Cron `*/5 * * * *`.
На початку кожного запуску Worker читає **публічний JSON**, який
зберігає наш бот ДТЕК:

[Графіки та стан DTEK-бота](https://github.com/XOTT69/dtek/blob/main/state/publications.json)

Схема: **ДТЕК → XOTT69/dtek → GitHub JSON → botvoda/D1 → закріплене табло, Telegram-бот і персональні нагадування.**

- Читаємо насамперед **`confirmedSchedules` з усіма 12 підтвердженими підгрупами**. Ці дані DTEK-бот зберігає до спроби публікації в Telegram. Для старих станів підтримується резервне читання `scheduleSnapshots`. Неповні дані, тижневі прогнози чи довільний текст Telegram не імпортуємо.
- В D1 зберігаємо **лише підгрупи 1.2 (вода) і 2.2 (світло)** для сьогоднішньої та завтрашньої дат. При новій даті автоматично додається відповідний графік.
- Якщо завтра ще **немає підтвердженого** графіка ДТЕК, його не вигадуємо й не перезаписуємо старі дані.
- Під час змін оновлюємо розрахунок води, світла й перетину, потім **редагуємо наявне закріплене текстове табло**. Окрема кольорова картинка графіка світла 2.2 редагується на місці й закріплюється другим повідомленням; нові пости при кожній зміні не створюються.
- Нові підтверджені графіки стають доступні в командах **«Сьогодні»** / **«Завтра»** та для персональних нагадувань.
- Повторні перевірки не переписують незмінний графік і не засмічують історію. Попередня версія зберігається для відкату.
- **Резервний графік водопостачання**, вручну встановлений фактичний стан і події про фактичну наявність електроенергії залишаються окремими.
- Тимчасова недоступність GitHub не зупиняє раніше збережені графіки та нагадування.

У приватній адмін-панелі **/admin → 🩺 Статус системи**
додано діагностику: коли Worker востаннє успішно прочитав
репозиторій ДТЕК, чи є дані на сьогодні та завтра,
а також які дати ще очікують підтвердження.
Зелена остання перевірка означає, що **саме запущений Worker**
виконував нову синхронізацію. Перевірка GitHub Actions
підтверджує лише коректність коду, але не активний деплой.

Після розгортання цього коду в Cloudflare Worker синхронізація ввімкнена
за замовчуванням і почнеться на найближчому Cron. Для ручної
перевірки власник бота може надіслати в особистий чат команду
**`/syncdtek`**: вона перевірить сьогодні й завтра, покаже що
оновлено, а якщо є зміни — оновить закріплений допис.

Вимкнення, якщо потрібне: Worker environment variable
`DTEK_AUTO_SYNC=off`. Інші токени, webhook-и й Cloudflare Worker
для репозиторію `XOTT69/dtek` не потрібні.

### Як активувати новий код у Cloudflare

Якщо `botvoda` уже підключений до **Cloudflare Workers Builds** з
автоматичним деплоєм гілки `main`, додаткових налаштувань не потрібно:
Cloudflare сам застосує коміт. Перевірити можна командою
`/syncdtek` **у приватному чаті з ботом**. Команда доступна тільки
власнику.

Якщо автодеплою немає, у GitHub додано ручний workflow
[Deploy water bot to Cloudflare](https://github.com/XOTT69/botvoda/actions/workflows/deploy-worker.yml).
Для нього одноразово потрібні **GitHub Actions repository secrets**:

- `CLOUDFLARE_ACCOUNT_ID` — Account ID вашого Cloudflare.
- `CLOUDFLARE_API_TOKEN` — обмежений API token з правом редагувати
  Cloudflare Workers Scripts для потрібного акаунта (за потреби також
  доступ до D1).

Після їх додавання: GitHub → Actions → **Deploy water bot to Cloudflare**
→ **Run workflow**. Робочі секрети Telegram у Cloudflare не потрібно
передавати в GitHub; вони залишаються у поточному Worker.

Цей workflow запускається **лише вручну**, щоб не створювати
подвійних деплоїв, якщо Cloudflare Builds уже працює. Без потрібних
секретів він зупиниться з поясненням — а не удаватиме, що успішно
розгорнув Worker.

Оновлення GitHub-репозиторію саме по собі **не підтверджує**, що новий
Worker уже працює в Cloudflare. Тільки після деплою нова
автосинхронізація виконуватиметься за Cloudflare Cron.

## Канал / група

Бот має бути адміністратором з правами публікувати, редагувати та закріплювати повідомлення. Картка графіка 2.2 генерується у власному SQLite Durable Object через SVG→PNG. QuickChart, платний ШІ й додаткові токени не потрібні. Чинний `TELEGRAM_BOT_TOKEN` і `publications.group_chat_id` використовуються повторно.

Початкове підключення: `/setupgroup`

Перевірка: `/checkgroup`

Ручне оновлення табло: `/refreshgroup`

Після підключення бот зберігає message_id і надалі редагує саме це повідомлення.

## Фактичний стан світла

У підключеному каналі бот автоматично розпізнає нові пости з фразами `Світло зникло` та `Світло з'явилось`. Час береться з тексту повідомлення, якщо він є.

Пріоритет у блоці **ЗАРАЗ**:

1. ручний стан із `/power`;
2. остання фактична подія з каналу;
3. графік групи 2.2.

Нова фактична подія з каналу автоматично скасовує ручний override. Старі пости Telegram заднім числом не надсилає, тому після першого deploy поточний стан можна один раз виставити через `/power`.

## Приватна адмін-аналітика

Команда `/analytics` і кнопка **📊 Аналітика** доступні тільки користувачу, чий Telegram ID збігається з `ADMIN_TELEGRAM_ID`.

Аналітика показує:

- загальну кількість користувачів;
- нових та активних за сьогодні / 7 / 30 днів;
- скільки людей прийшло через `?start=chabany` із кнопки каналу;
- активні типи нагадувань і вибір 15 / 30 / 60 хв;
- кількість фактично відправлених нагадувань;
- останніх користувачів з ім'ям, username, джерелом та останньою активністю;
- денну активність за останні 7 днів.

Старі користувачі автоматично переносяться в аналітику з Telegram ID. Ім'я та username доповнюються після їх наступної взаємодії з ботом.

## 💧 Фактична вода: повідомлення мешканців

У приватному чаті з ботом доступна кнопка **💧 Стан води** та команди
`/waterstatus` і `/reportwater`. Користувачі повідомляють **💧 Вода є** або
**🚱 Води немає**, а також бачать підсумок останніх повідомлень.
Із закріпленого канального табло можна відкрити бота кнопкою
**💧 Повідомити про воду**.

- У D1 зберігається **лише останній стан одного Telegram ID**, без публікації
  імен, акаунтів або індивідуальних голосів.
- У підсумку враховуються лише відповіді за **останні 45 хвилин**; старі
  повідомлення не створюють безстрокового «факту».
- Для переважного стану треба **не менше двох** узгоджених повідомлень і
  щонайменше **75%** голосів одного типу. Інакше бот показує «суперечливі»,
  «недостатньо» або «немає свіжих».
- Повтор однакового стану можливий не частіше ніж раз на **10 хвилин**,
  зміна стану — не частіше ніж раз на **2 хвилини**.
- Після повідомлень редагується чинне закріплене табло, **без окремих постів
  чи масових сповіщень**. Застарілі записи очищаються через 14 днів.
- Опитування **не змінює офіційний графік**, адміністративний ручний стан
  `/water` або логіку сповіщень. Статус позначений як слова мешканців,
  а не показник датчика чи перевірена наявність у кожному будинку.

Нові таблиці автоматично створюються через `ensureSchema`; налаштування
Cloudflare D1, токени та ручні міграції не потрібні. Перед випуском виконайте
`npm test`; для перевірки синтаксису Worker виконайте
`npx wrangler deploy --dry-run`.

## Окрема картка графіка 2.2

Картка використовує чинну прив’язку `/setupgroup` і зберігає свій
`photo_message_id` у тому самому D1, окремо від ID текстового табло.
Нові Secrets і повторне підключення бота не потрібні. Webhook не переноситься.

- На картці завжди є сьогодні; без даних показано «Графік ще не опублікований».
- Завтра додається тільки після отримання підтвердженого графіка 2.2.
  Порожній список відключень — підтверджена відсутність планових відключень,
  а не відсутність даних.
- На першому cron після зміни київської дати вчора зникає, а підтверджене
  завтра стає сьогодні. Свіжий графік на наступний день додається за наявності.
- Час «Оновлено» змінюється лише разом із датою/годинами або версією дизайну.
  Незмінні дані не запускають рендер і не відправляються до Telegram повторно.
- Картка має кнопку «📊 Відкрити моніторинг». За потреби URL змінюється
  необов’язковою змінною `MONITORING_URL`.
- ID фото зберігається до закріплення. Нестача прав на закріплення не створює
  ще одного фото. Підтверджена Telegram помилка про видалене фото дозволяє
  створити одну заміну; помилки прав чи мережі не є приводом її створювати.
- D1 захищає від паралельного надсилання. Невідомий результат `sendPhoto`
  переводить картку в `uncertain`: автоматичні повтори зупинені, щоб не
  дублювати фото. `/checkgroup` показує цей стан. Перед відновленням такого
  випадку адміністратор має звірити канал і D1; не слід сліпо скидати стан.

### Ввімкнення та зупинка

Код вимкнено за замовчуванням. Після перевірки дизайну й розгортання додайте
у Cloudflare Worker **botvoda → Settings → Variables and Secrets** текстову
змінну `SCHEDULE_CARD_ENABLED` зі значенням `on`.
Значення `off` або відсутність змінної припиняє будь-які дії з фото, не
видаляє його й не змінює роботу текстового табло.
Новий renderer binding і SQLite DO migration оголошені в `wrangler.jsonc`.
Існуючий binding `DB` збережено; колонки картки додаються автоматично.
`keep_vars` зберігає змінні, задані через Cloudflare Dashboard.

Генерація не використовує зовнішнього платного сервісу. На Cloudflare Free
діють загальні квоти Workers/D1/Durable Objects; гарантії необмеженої роботи
немає. Рендер працює всередині Durable Object із власним бюджетом CPU,
а не в 10 мс CPU звичайного безкоштовного Worker. Бот перевіряє графік
кожні 5 хвилин, а малює лише при зміні вмісту.

### Локальна перевірка

`npm test` перевіряє чинні функції та життєвий цикл картки.
`npm run check` збирає Worker без розгортання.
`npm run preview:card` запускає лише локальний renderer без Telegram і
production D1 та зберігає два PNG з демонстраційними годинами в `outputs/`.
Шрифти Noto Sans Regular/Bold взято з `notofonts/noto-fonts`, ліцензія OFL
лежить у `src/assets/NotoSans-LICENSE.txt`.

### Cloudflare PR Previews

Для гілок Cloudflare Builds запускає `npx wrangler preview`. Блок `previews`
у `wrangler.jsonc` підключає окремий renderer namespace та не підключає D1.
`PREVIEW_MODE=on` залишає доступними лише текстову головну сторінку та
`/preview-card.png?days=1` / `/preview-card.png?days=2`.
Це зразки дизайну з вигаданими годинами й поміткою «ДЕМОНСТРАЦІЯ».
Webhook/setup-маршрути та cron блокуються до будь-яких звернень до ресурсів
бота. Telegram-відправки у Preview не виконуються. Production-конфігурація
з D1, cron і вимкненою за замовчуванням карткою збережена окремо.

### Контрольований запуск у production

Штатний workflow **Deploy water bot to Cloudflare** має режим `inspect`
за замовчуванням. Він лише звіряє binding D1, знаходить єдине підключення
Покровської та показує поточну версію deployment, без записів у D1 чи Telegram. Якщо API-токен не має D1 Read, адресат звіряється всередині Worker через чинний binding DB.
`mode=deploy` розгортає код; прапорець `enable_schedule_card=true` вмикає
картку лише для єдиного підключення з назвою Покровської 30Б. За кількох або відсутніх збігів публікація зупиняється. Необов’язкова змінна `SCHEDULE_CARD_CHAT_ID` дозволяє явно вибрати одне з наявних підключень.
Вже збережені Cloudflare Secrets використовуються всередині GitHub Actions;
їхні значення не виводяться в журнал і не передаються в код репозиторію.
